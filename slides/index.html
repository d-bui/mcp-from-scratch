認証層 ①

人間ユーザー ― ログインしてセッショントークン

api/auth/userAuth.mjs
// ログイン成功 → セッショントークン（usr_ プレフィックス）を発行
export function login(login_id, password) {
  const found = LOGIN_USERS.find((u) =>
    u.login_id === login_id && u.password === password);
  if (!found) return null;
  const token = "usr_" + randomUUID();
  sessions.set(token, { login_id: found.login_id, name: found.name });
  return token;
}

// ガード:「人間ユーザー専用」API に付ける（更新・削除など）
export function userOnly(req, res, next) {
  if (req.actor?.type === "user") return next();
  return res.status(403).json({ /* code: "user_only" */ });
}

実務では JWT + httpOnly Cookie（spx は JWT 30 日 Cookie）。デモはメモリの Map で最小構成。

認証層 ②

AI エージェント ― ログインではなく事前発行キー（PAT）

api/auth/agentAuth.mjs
// 人間のログインとは完全に別系統。セッションを持たない。
// デモは env から読むが、実務では DB に保存する:
//   - 管理者ごとに発行し、ハッシュ化して api_keys テーブルへ
//     （平文は発行時に一度だけ表示）
//   - トークン → 所有者を引けるので監査ログに残せる
//   - 無効化・ローテーションが DB の 1 レコード操作でできる
const AGENT_KEYS = (process.env.AGENT_API_KEYS ?? "agent-demo-key")
  .split(",").map((s) => s.trim()).filter(Boolean);

export function resolveAgentToken(token) {
  return AGENT_KEYS.includes(token) ? { key: token } : null;
}

別系統にする理由: 失効・監査・レート制限を人間と別に設計できる。キー 1 本で「どの AI 接続か」まで追える。

認証層 ③

入口で「誰か」を確定する ― actor 判定ミドルウェア

api/server.mjs
// Bearer トークンを見て actor（誰が呼んでいるか）を確定する
app.use("/api", (req, res, next) => {
  const token = (req.headers.authorization ?? "")
    .replace(/^Bearer\s+/i, "");

  const session = resolveUserToken(token);      // ① 人間？
  if (session) { req.actor = { type: "user", name: session.name }; return next(); }

  const agent = resolveAgentToken(token);       // ② AI？
  if (agent) { req.actor = { type: "agent" }; return next(); }

  res.status(401).json({ /* code: "unauthorized" */ }); // ③ 拒否
});

以降の全ルートは req.actor.type（"user" | "agent"）だけを見ればいい。判定は 1 箇所。

公開レジストリ（このデモの肝）

AI に許す API は「明示的な登録制」

api/agentRegistry.mjs
// ここに登録された API だけが AI エージェントから呼べる
export const AGENT_APIS = [
  { name: "list_users",  method: "GET",  path: "/api/users" },
  { name: "get_user",    method: "GET",  path: "/api/users/:id" },
  { name: "create_user", method: "POST", path: "/api/users" },
  // update / delete は意図的に登録しない = 破壊的操作は人間専用
];

export const forAgent = (name) => (req, res, next) => {
  if (req.actor?.type === "user") return next();  // 人間は常に OK
  if (AGENT_APIS.some((a) => a.name === name)) return next();
  return res.status(403).json({ /* code: "agent_not_allowed" */ });
};

パスのプレフィックスで開放すると隣のセンシティブな API まで開く事故が起きる（実運用のヒヤリ経験）。1 本ずつの登録制なら、この表がそのまま AI 向け API 仕様書になる。

結果

権限マトリクス ― 同じ API、違う権限

API人間ユーザーAI エージェント
GET /api/users（一覧）✔✔ 登録済み
GET /api/users/:id（取得）✔✔ 登録済み
POST /api/users（作成）✔✔ 登録済み
PUT /api/users/:id（更新）✔✘ user_only
DELETE /api/users/:id（削除）✔✘ user_only
GET /api/agent/apis（公開一覧）✔✔ 登録済み

エラーコードも 2 種類: user_only = 人間専用ガード付き、agent_not_allowed = レジストリ未登録。AI は自分の使える一覧を自分で取得できる（/agent/apis）。

3 層の分離

1 リクエストが 3 層を通る ― POST /api/users の例

controller ― HTTP とガードだけ
usersRouter.post("/", forAgent("create_user"),
  handle((req, res) => ok(res, usersService.create(req.body ?? {}), 201)));
service ― 業務ルールだけ（HTTP を知らない）
create(input) {
  validate(input);  // name / email / role
  if (usersRepository.findByEmail(input.email))
    throw new ServiceError(409, "email_taken", "その email は既に使われています");
  return usersRepository.create({ ... });
}
repository ― 保存だけ（実務は MySQL に差し替え）
create({ name, email, role }) {
  const user = { id: nextId++, name, email, role };
  users.set(user.id, user);
  return user;
}
MCP 層

MCP は「API 説明層」 ― 説明文がそのまま AI への指示書

mcp/index.mjs
tool(server, "create_user", {
  title: "ユーザー作成",
  description: "ユーザーを新規作成する。email が既存と重複すると失敗する
    （email_taken）ので、事前に list_users で確認するとよい。",
  inputSchema: {
    name:  z.string().min(1).describe("氏名"),
    email: z.string().describe("メールアドレス（重複不可）"),
  },
}, async ({ name, email, role }) =>
  ok(await api("POST", "/users", { name, email, role })));

// 接続時に渡す運用ルール（instructions）:
//  「ID は推測せず必ず list_users で解決」
//  「更新・削除はできない → 管理画面を案内」

MCP 層は DB に触れず、権限も持たない。PAT で REST API を呼ぶだけ — 権限判定・バリデーションは API 側 1 箇所。AI の振る舞いはコードではなく文章（description）で制御する。

配布・デプロイ

デプロイ単位が違う ― API は Docker、MCP は .mcpb

  • API サーバー → Docker コンテナ
    サーバー側で稼働（実務なら ECS 等）
  • MCP サーバー → .mcpb ファイル
    利用者の PC で Claude が stdio 起動。Node 不要・ダブルクリックで導入
  • API URL とキーはインストール時のフォーム入力
    sensitive キーは OS キーチェーンに保存
manifest.json（.mcpb）
"server": {
  "type": "node",
  "entry_point": "mcp/index.mjs", ...
},
"user_config": {
  "api_key": {
    "title": "エージェント用アクセスキー",
    "sensitive": true,
    "required": true
  }
}
ライブデモ

デモ手順 ― この順で見せます

  • npm run docker — API 起動（localhost:3000）
  • curl で人間フロー: ログイン → 一覧 → 削除も OK
  • curl で AI フロー: PAT で一覧 OK → 削除は 403（user_only）
  • npm test — MCP を SDK クライアントで E2E 検証（12 項目、異常系込み）
  • Claude Code / Desktop から実際に会話で操作（.mcp.json / .mcpb）

「3 番を削除して」と頼むと、AI は削除ツールを持たないので管理画面を案内してくる — ここが見せ場。

実運用からの学び

65 ツール運用して分かったこと ― spx-learning-square より

  • MCP 層は権限を持たせない — 壊れても UI にできない事故は起きない
  • 認証は人間と AI で別系統 — 失効・監査・レート制限を独立に設計
  • AI への公開は登録制 — プレフィックス開放は事故のもと
  • エラーは throw せず isError + 機械可読 code — AI が自力でリカバリーできる
  • stdout は JSON-RPC 専用 — console.log 1 行で通信が壊れる
  • ツールの description = AI への指示書 — 挙動は文章で制御する
