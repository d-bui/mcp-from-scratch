全体像

入口は 2 つ、中身は 1 つ ― 同じサーバーを人間と AI が使う

人間
ログインして入館証（トークン）をもらう
AI（Claude）
合鍵（アクセスキー）で入る。説明係（MCP）を連れている
⟶⟶
受付ゾーン 来たのが人間か AI かをここで見分ける
AI がやっていいことリスト AI に許す操作はここに書いたものだけ
窓口 お願いを受けて、返事を返す
ルール係 入力チェック・重複チェック
保管係 データを保存する

大事なことは 2 つ。「誰が来たか」は受付が決める。「AI に何を許すか」はリストが決める。

役割分担

7 つの係に分けた ― 1 つの係 = 1 つのファイル

係ファイルやること（一言で）
受付（人間用）api/auth/userAuth.mjsログイン → 入館証を発行。「人間だけ」の扉も守る
受付（AI 用）api/auth/agentAuth.mjs事前に渡してある合鍵（アクセスキー）を確認する
やっていいことリストapi/agentRegistry.mjsここに書いた API だけ AI が使える
窓口api/usersController.mjsお願いを受けて、返事を返す
ルール係api/usersService.mjs入力チェックや「email 重複はダメ」などのルール担当
保管係api/usersRepository.mjsデータを保存するだけ（今回は勉強用にメモリ保存）
AI への説明係mcp/index.mjsAPI の使い方を AI に日本語で教えながら取り次ぐ

係を分けておくと、「AI まわりを変えたい」ときにどのファイルを触ればいいかがすぐ分かる。

ポイント① 入口は人間と AI で分ける ― 人間側

人間の入口 ― ログインして入館証をもらう

api/auth/userAuth.mjs
// ログイン成功 → 入館証（usr_ で始まるトークン）を発行
export function login(login_id, password) {
  const found = LOGIN_USERS.find((u) =>
    u.login_id === login_id && u.password === password);
  if (!found) return null;
  const token = "usr_" + randomUUID();
  sessions.set(token, { login_id: found.login_id, name: found.name });
  return token;
}

// 「人間だけ」の扉。AI が来たら断る（削除・更新など）
export function userOnly(req, res, next) {
  if (req.actor?.type === "user") return next();
  return res.status(403).json({ /* 「人間専用です」 */ });
}

いつもの Web サービスと同じ流れ。今回は勉強用に一番シンプルな形にしてある（本番では Cookie などを使う）。

ポイント① 入口は人間と AI で分ける ― AI 側

AI の入口 ― ログインなし。合鍵（アクセスキー）で入る

api/auth/agentAuth.mjs
// AI は人間と別の入口から入る。ログインではなく、
// 事前に渡してある合鍵（アクセスキー）を見せてもらう方式。
//
// 本番では鍵を DB に保存する:
//   - 1 人ずつ発行できる（誰の鍵か分かる → 記録が残せる）
//   - 使わせたくなくなったら、その鍵だけ止められる
const AGENT_KEYS = (process.env.AGENT_API_KEYS ?? "agent-demo-key")
  .split(",").map((s) => s.trim()).filter(Boolean);

export function resolveAgentToken(token) {
  return AGENT_KEYS.includes(token) ? { key: token } : null;
}

入口を分けておくと、「AI の鍵だけ止める」「AI の利用だけ記録する」が簡単にできる。

ポイント① 入口は人間と AI で分ける ― 見分け方

入口で「人間か AI か」を見分ける

api/server.mjs
// 見せられたトークンを確認して、「誰が来たか」を決める
app.use("/api", (req, res, next) => {
  const token = (req.headers.authorization ?? "")
    .replace(/^Bearer\s+/i, "");

  const session = resolveUserToken(token);      // ① 入館証？ → 人間
  if (session) { req.actor = { type: "user", name: session.name }; return next(); }

  const agent = resolveAgentToken(token);       // ② 合鍵？ → AI
  if (agent) { req.actor = { type: "agent" }; return next(); }

  res.status(401).json({ /* どちらでもない → お断り */ });
});

見分けるのは入口の 1 箇所だけ。後ろの係たちは「人間か AI か」の結果を使うだけでいい。

ポイント② 許可はリストで（今日いちばん大事）

AI に許す操作は「リストに書いたものだけ」

api/agentRegistry.mjs
// AI がやっていいことリスト。ここに書いた API だけ AI が使える
export const AGENT_APIS = [
  { name: "list_users",  method: "GET",  path: "/api/users" },
  { name: "get_user",    method: "GET",  path: "/api/users/:id" },
  { name: "create_user", method: "POST", path: "/api/users" },
  // 削除・更新はわざと書かない = 人間にしかさせない
];

export const forAgent = (name) => (req, res, next) => {
  if (req.actor?.type === "user") return next();  // 人間はいつでも OK
  if (AGENT_APIS.some((a) => a.name === name)) return next();
  return res.status(403).json({ /* 「AI には開放していません」 */ });
};

「この辺は全部 OK」とざっくり開けると、開けたくないものまで開いてしまう事故が起きる（実体験）。1 個ずつ書く方式なら、この表を見るだけで「AI にできること」が全部わかる。

ポイント② の結果

同じ API でも、できることが違う

操作人間AI
ユーザー一覧を見る✔✔ リストにある
ユーザーを 1 人見る✔✔ リストにある
ユーザーを追加する✔✔ リストにある
ユーザーを更新する✔✘ 人間専用
ユーザーを削除する✔✘ 人間専用
「AI にできること」の一覧を見る✔✔ リストにある

削除・更新はリストに書いていないので、AI は頼まれてもできない。しかも AI は「自分に何ができるか」を自分で確認できる（一番下の API）。

ポイント③ 係を分けて小さく保つ

1 つのお願いが 3 つの係を通る ― 「ユーザー追加」の例

窓口 ― 受けて、渡して、返事するだけ
usersRouter.post("/", forAgent("create_user"),
  handle((req, res) => ok(res, usersService.create(req.body ?? {}), 201)));
ルール係 ― チェック担当（「email 重複はダメ」など）
create(input) {
  validate(input);  // 名前・email・役割をチェック
  if (usersRepository.findByEmail(input.email))
    throw new ServiceError(409, "email_taken", "その email は既に使われています");
  return usersRepository.create({ ... });
}
保管係 ― 保存するだけ
create({ name, email, role }) {
  const user = { id: nextId++, name, email, role };
  users.set(user.id, user);
  return user;
}
ポイント④ AI の動きは「説明文」で決まる

MCP は「AI 向けの取扱説明書」つきの窓口

mcp/index.mjs
tool(server, "create_user", {
  title: "ユーザー作成",
  description: "ユーザーを新規作成する。email が既存と重複すると失敗する
    ので、事前に list_users で確認するとよい。",
  inputSchema: {
    name:  z.string().min(1).describe("氏名"),
    email: z.string().describe("メールアドレス（重複不可）"),
  },
}, ...);

// つないだ瞬間に AI へ渡す「お約束」も文章で書く:
//  「ID は推測しないで、必ず一覧で確認してから」
//  「削除を頼まれたら、管理画面を案内して」

この説明文がそのまま AI への指示書になる — こう書いておくと AI がその通りに動く。説明係は API を呼ぶだけで、特別な権限は持っていない。

ポイント⑤ 届け方

置き場所が違う ― API はサーバーに、説明係は各自の PC に

  • API サーバー → Docker でサーバーに置く
    みんなで 1 つを使う
  • 説明係（MCP） → .mcpb という 1 ファイルを配る
    各自の Claude にダブルクリックで入る。難しい設定は不要
  • 鍵はインストール時に 1 回入力するだけ
    PC の安全な場所（キーチェーン）に保存される
manifest.json（.mcpb の設定）
"user_config": {
  "api_key": {
    "title": "エージェント用アクセスキー",
    "sensitive": true,  // ← 安全に保存
    "required": true
  }
}

Claude に「3 番を削除して」と頼むと、削除の道具を持っていないので「管理画面からどうぞ」と案内してくる — ここが見せ場。

実運用からの学び

本番で 65 個のツールを運用して分かったこと

  • 説明係（MCP）に権限を持たせない — 壊れても事故にならない
  • 人間と AI の入口を分ける — 止める・記録する・制限するを別々にできる
  • AI に許すことはリストで管理 — ざっくり開放は事故のもと
  • エラーは「理由つき」で返す — AI が読んで自分でやり直せる
  • AI の動きはコードより「説明文」で決まる — 書き方が一番効く
